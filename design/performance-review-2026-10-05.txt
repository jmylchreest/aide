Performance review — 2026-10-05

Implemented
Issue #62: non-source files and dotfiles reach secrets analysis while code indexing and
source analyzers retain grammar gating. Full/incremental secrets share a 1 MiB limit,
regular-file and checkout checks, ignore handling, and bounded reads. Source analyzers
share their content read. Each changed-file batch lazily shares a scanner, serialized
for safety and closed when its jobs finish, including cancellation before dispatch.
Deletion cancels and drains old per-file work before clearing findings.

Watcher: redundant roots are removed; watch count comes from the live backend.
Generated versioned documentation and retrieval outcome snapshots are excluded in
.aideignore. These exclusions reduce automatic coverage deliberately. An earlier
checkout count was 461 directories; 176 were versioned documentation and 118 were
retrieval directories. Keep current documentation and the retrieval harness watched.
Linux fsnotify needs a watch per directory; 463 watches alone did not explain the
measured memory. The major cost was analyses scheduled by events and startup.

Search storage: replace operations use bounded 128-operation Bleve batches instead
of building/committing one search segment per record. Existing Bolt persistence,
store boundaries, document identity and search visibility locks remain in place.
Errors from batch commits propagate; as before, Bolt and Bleve are not one atomic
transaction. Regression tests cover >128 items, replacement, stale search removal,
unrelated analyzers, clearing and counts.

Clones: immediately discard overflowing hash-bucket locations while keeping a
sentinel for skipped-bucket counts; avoid allocating language groups for singleton
buckets. MaxBucketSize must be configured before AddFile, as production already does.
Unlimited buckets remain unlimited. Tests verify boundary, overflow, other groups,
skipped counts and unlimited behavior.

Measurements
Benchmark runs use identical benchmark sources, three one-iteration runs for the
scanner and three repetitions of three iterations for storage and clone operations.
- Eight changed Go files: 128 MB -> 17–18 MB allocated; 59–64 ms -> 23–26 ms.
- Replace 100 findings: 180–193 MB -> 2.32–2.33 MB allocated;
  90–131 ms -> 3.97–4.28 ms.
- Clone singleton grouping, 10,000 hashes: 640 KB/10,000 allocations -> zero.
- Repeated clone boilerplate: 26.55 MB -> 165 KB allocated.
These are operation allocation measurements, not retained RSS or universal latency.

RSS interpretation
The optimized cold run retained about 19 MB HeapInuse after forced GC, but had
314 MB HeapSys and only 87 MB HeapReleased. RSS also includes native C allocations
from tree-sitter, mapped BoltDB pages and executable pages. The largest index mapping
was approximately 55 MB resident; the fixture and binaries reside on tmpfs here,
so mapping accounting differs from a normal disk-backed checkout. No retained Go
heap leak was demonstrated. Do not set a global forced-GC ticker or claim a soft Go
memory limit controls native allocations. RSS readings vary with scavenging and
host paging; profiles expose more than the number of watches.

Remaining significant opportunities, in priority order
1. Findings replacement scans and JSON-decodes the entire Bolt bucket for every
   file/analyzer update (searchableStore.replace). Add a maintained analyzer/file
   secondary index or coalesce a watcher batch into one replacement transaction.
   This needs migration/rebuild and acceptance-state tests, rather than an untested
   schema shortcut. Likely best next step on large finding sets.
2. Clone and dead-code computations do not honor cancellation throughout their
   implementations. Superseded project work can keep token arrays, trees and complete
   symbol/reference snapshots alive until completion. Thread context through walks,
   tokenization, hashing and verification; test that cancellation actually drains
   workers. Preserve serialized/coalesced project scheduling.
3. Reduce native tree-sitter concurrency and measure RSS versus latency on large
   repositories. Walks currently allocate Node wrappers for individual children;
   cursor traversal may also reduce Go allocations. Native allocation profiling
   is needed before choosing worker limits or platform allocator tuning.
4. Search mapping rebuild indexes one record at a time; use the same bounded batch
   approach during real upgrade/rebuild benchmarks. Stats load whole record slices
   through allMatching; aggregate during iteration to reduce temporary retention.
5. Dead-code reference verification copies full symbol/reference sets and caches
   complete source files for a run. Stream/index lookups could reduce peak memory.
   The custom bytesIndex scan also appeared at about 3% CPU in one post-fix profile;
   benchmark standard bytes.Index before replacing it, retaining empty/boundary rules.
6. Titus portable regex matching remains a large CPU consumer after constructor
   reuse. Avoid weakening rules to speed it up; explore safe scanner pools or cheaper
   candidate filtering only with coverage and end-to-end throughput measurements.

Broader codebase review — follow-up

Scope: reviewed the main daemon, plugin and web execution paths below, with
existing Go benchmarks run across pkg/... and repeated expensive cases. This is
a cross-subsystem performance review, not a claim that every line, platform or
browser interaction has been profiled. Timing figures are local synthetic
benchmarks; the original separate-repository daemon profiles remain the RSS evidence.

Coverage and evidence
- Watcher/findings: original pprof, scanner/read sharing and project scheduling;
  cancellation and large-source-file reads remain priorities from the first review.
- Parser/grammar: code parser benchmark, loader language/negative caches, native
  tree lifetimes. Language caches are intentional; process-native allocation
  profiling and worker-count experiments are still needed for RSS attribution.
- Code index/store: checkout cold, bulk, seeded, unchanged and query benchmarks;
  codeindex.Run already batches 32 files or 8 MiB and honors cancellation.
  Cold indexing is much more expensive than unchanged reconciliation; avoid
  gratuitous startup rebuilds. Seeded indexing still builds the local search index.
- Memory/search: SearchMemories and ListMemories benchmarks, combined store
  hydration and search analyzers. Repeated scored search over 400 memories costs
  about 0.51 MB and 2.6 ms per request. Initial ~7 MB single-shot search was a
  cold/background-merge effect, not representative steady-state evidence.
  ListMemories scans/decode-all and slices after filtering; a positive limit
  does not bound work and the slice backing array retains excess pointers.
- Observe/token telemetry: ListObserveEvents, ListTokenEvents and TokenStats
  cursor passes, attribution and model-usage dedup. New history-growth benchmarks
  show real scaling costs even with small requested pages (see below).
- Event fanout/gRPC streaming: broadcaster, streaming server callers and web SSE
  forwarding. Reproduced and fixed a live-parent cancellation-goroutine leak and
  a send-versus-channel-close race. Existing stream buffers and context cancellation
  paths were inspected; drop policy and store reconciliation remain unchanged.
- MCP response observation: cmd_mcp middleware counts returned TextContent bytes
  rather than serializing an entire response a second time. Large responses still
  create strings/transport buffers; use caller result limits where meaningful.
- Survey: git history/freshness, module graph and call-graph paths plus benchmarks.
  Commit walks cap at 500; graph traversal caps nodes/depth; module symbol lookups
  cache definers within the run. Expensive git diff/blame work is explicit survey
  work, not a permanent watcher task. No new shortcut that breaks go-git portability.
- Context sharing/subscriptions: export/import and subscription sync paths.
  Exports intentionally enumerate records, and writers skip identical file content.
  Subscription freshness uses timestamps and stale-cache fallback; preserve the
  existing project/decision isolation rather than share arbitrary process caches.
- Plugin hooks: aide-client, tool-observe, session-init and model-usage.
  Repeated execFileSync calls spawn clients and block hooks. Benchmark a whole
  tool-call hook with a live daemon before replacing the portable CLI boundary
  with a long-lived/batched transport. Current adapter usage batches already
  avoid one subprocess per usage row; transcript tails and dedup caches are bounded.
- Context pruning: tracker and dedup. History is capped at 200 records but retains
  original/pruned outputs with no aggregate byte budget. Count limits alone do not
  protect RSS from a few huge outputs; add a byte budget preserving dedup/recovery
  semantics, and measure long OpenCode sessions. Not quantified in this review.
- Web server/UI: instance health loops, SSE forwarding, APIReadFile, useApi,
  useObserveEvents and event batching. Observe buffers are capped (default 1,000)
  and updates batched. APIReadFile reads the entire file before enforcing its 500 KiB
  response cap: precheck regular-file size and use a bounded read to control request
  memory. useApi does not abort obsolete requests; rapid filter changes can leave
  unnecessary requests in flight. Browser heap/render profiling was not performed.
- Instinct/reflection: runner and catalogue event processing. Output limits do not
  bound the input event histories; improve store query paths first, then profile
  catalogue parsers with realistic cross-session histories. No LLM-only parser was
  enabled merely for a performance experiment.

TokenStats scans/decodes history twice, and a third time when retrieval windows
require context. Session/date filters are applied late because attribution,
usage conflict handling and retrieval context depend on related evidence.
Do not simply break an ID-ordered cursor: timestamps can be backfilled and differ
from IDs. Prefer timestamp/session indexes with migration/rebuild support and
bounded top-k selection for pages. Preserve cross-window conflicts, delegation,
attribution and dedup semantics in aggregation changes. These are the most
significant newly measured opportunities for projects with long event histories.

Implemented subscription lifecycle fix
context.AfterFunc replaces one waiting goroutine per subscription; manual unsubscribe
stops its callback registration even while the parent context remains live.
Per-subscription send/close synchronization prevents a snapshotted publisher from
sending after unsubscribe closes the channel. Filters run outside that lock so a
filter can unsubscribe safely.
Both regression tests fail on the old implementation: 100 unsubscribed streams
retain 100 goroutines, and unsubscribe during a paused filter produces a recovered
send-on-closed-channel panic. Both pass after the fix.
For 1,000 subscribe/unsubscribe operations, the benchmark reports 1,000 retained
goroutines before and zero after. Allocation/latency results for churn varied;
no general allocation reduction is claimed. The safety lock increases single-
subscriber publishing from ~137–138 ns to ~151–157 ns and median 128-subscriber
publishing from ~5.7 microseconds to ~6.4 microseconds. This tradeoff removes an actual
panic and retained idle goroutines; transport I/O is not represented by this microbench.
