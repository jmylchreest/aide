# hud-wrapper-root-resolution

**Decision:** The installed HUD wrapper resolves the plugin root in a fixed order: AIDE_PLUGIN_ROOT/CLAUDE_PLUGIN_ROOT, then the pointer file ~/.claude/bin/aide-hud.path written by session-start, then the marketplace cache walk. Never parse Claude Code's installed_plugins.json.

## Rationale

The statusline is a user-settings command, not a plugin hook, so it inherits no CLAUDE_PLUGIN_ROOT and cannot locate the plugin itself. session-start already resolves the root via getPluginRoot(), so the knower records it rather than the guesser guessing. installed_plugins.json is rejected as a source because it is Claude Code's private schema (already version 2) and does not exist under OpenCode, which the cross-platform-compatibility decision requires supporting.

## Details

The pointer is a sidecar file, not a path baked into the wrapper body: the plugin root changes on every upgrade or reinstall while the wrapper version changes rarely, and shouldInstallWrapper must keep refusing to rewrite a wrapper whose version is not strictly lower. A baked-in path would need a rewrite that rule would correctly refuse, leaving it pointing at a deleted directory. session-start writes the pointer before both early returns in installHudWrapper so it tracks the current install every session, including from the OpenCode package which ships no scripts/ of its own. Cost also matters: the statusline repaints roughly every 300ms, so the old cache walk was a recursive readdir per tick where the pointer is one existsSync plus a small read. The wrapper cannot import from the plugin, since locating the plugin is its whole job, so it inlines the pointer filename; tests pin that inlined copy against HUD_POINTER_FILENAME and the tier order because drift between the two copies is how this breaks again. Failure text is 'hud unavailable', never 'not installed' — hooks, MCP and skills resolve independently and can all be working when this lookup fails.
